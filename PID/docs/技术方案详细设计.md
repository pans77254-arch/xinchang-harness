## 0. 编写原则（先读）

1. **投标方案技术条款为硬约束。** 模型选型、三条业务路径、六层架构、六类智能体、微件化、指标口径等，本文只做「怎么落地」，不改「承诺什么」。
2. **本文补充的是开发可执行设计：** 固定工作流怎么串、工具与智能体怎么分、Skill/工作流注册怎么挂、前后端怎么调、审查点怎么交。
3. **若表述冲突：以投标为准。** 内部讨论中的接口名、目录名、实现库，服从投标对外口径。
4. **禁止事项：** 为单个审查点另起总控；前端直连大模型；后端服务层写审查算法；客户改规则就改编排边。

### 0.1 投标不可违背清单（摘要）

| 类别 | 投标承诺（必须守住） |
|------|----------------------|
| 总逻辑 | 规则数字化 → 图纸结构化 → 审查智能化 → 结果可视化 |
| 混合架构 | 多模态大模型智能体 + CV-CAD 协同 + 图计算推理；单一模型不包办 |
| 形式路径 | **PP-DocLayoutV3** 定位区域 → **Qwen3.8** 抽 JSON → **规则引擎**按技能校验 → 目录三方比对 |
| P&ID 路径 | **Image-to-Graph**（Swin+Transformer）→ 图库 → 规则转 Cypher 等拓扑校验 |
| 总图路径 | **CV+CAD 协同**；MCP 控 CAD；量距回阈值 |
| 编排 | **LangGraph** 多智能体协同 |
| 智能体 | **六类**：形式/P&ID/总图 **规则转换×3** + 形式/P&ID/总图 **审查执行×3** |
| 分层 | 资源 / 数据 / AI引擎 / 智能体 / 服务 / 展现 |
| 工程 | 微件化；二维协同标准化接口；内网私有化；知识产权归招标人 |

### 0.2 本文补充但不违背之处

| 补充点 | 说明 | 与投标关系 |
|--------|------|------------|
| 执行面固定链 | 识别 → 抽取 → 校验（由总控编排） | 落实「LangGraph 统一工作流图」，不是替换六智能体 |
| 工作流/Skill 包 | 审查点 = 注册中心里的技能描述（`needs`+`checks`） | 对应投标「规则技能 / 机器可执行技能」 |
| 工具层预处理 | PDF→PNG、DOC→MD 等**不走智能体** | 落在「图纸解析与预处理 / AI引擎」，不新增业务 Agent |
| 编译面 vs 执行面 | 改规则走转换智能体；日常审图走执行链 | 对应投标「规则翻译 → 审查执行」 |
| 前后端边界 | Vue3 不直连智能体；RuoYi 不写审查算法 | 符合服务层/展现层职责 |
| `layout.detect` 接口 | **实现体为 PP-DocLayoutV3**（投标基座） | 统一调用名，不改变投标选型 |

> 说明：内部骨架文件名若出现 `layout_yolo` 等历史命名，**对外与验收口径仍以 PP-DocLayoutV3 为准**；实现上应切换/封装为投标基座模型，或保留同接口可替换但默认投标选型。

## 1. 总体实现思路（对齐投标）

### 1.1 一句话

构建基于「**多模态大模型智能体 + 计算机视觉 CV-CAD 协同 + 图计算推理**」的混合架构智能审查系统，覆盖形式审查与目录一致性、工艺自控流程图（P&ID）审查、总平面布置图审查；松耦合微件化，支持独立开发部署与二次扩展。

### 1.2 分工原则（投标原文落地）

| 能力 | 承担方 | 不做什么 |
|------|--------|----------|
| 规则理解、任务分析、统筹调度 | 多模态大模型智能体（经 LangGraph 编排） | 不替代 CAD 精确量距 |
| 复杂视觉理解、版面/轮廓 | CV（含 PP-DocLayoutV3 等） | 不独自完成拓扑合规判定 |
| 拓扑关系推理 | 图数据库 + 图结构（I2G 产出） | 不用关系库硬 JOIN 扛多跳 |
| 图层筛选与空间计算 | CAD（精确几何） | 不负责语义「看懂」图例 |

### 1.3 系统上下文

```
二维协同 / 人工上传
        ↓
展现层 Vue3（门户·预览·规则·复核·统计）  ──不直连──×──→ 大模型
        ↓ HTTPS API
服务层 RuoYi（任务·权限·落库·队列·协同网关）──不写──×──→ 审查算法
        ↓ invoke(task)
智能体层 LangGraph 总控
        ↓
AI 引擎 + 工具（检测/抽取/I2G/CAD/向量…）
        ↓
数据层（库·图·对象存储·规则库·工件库）
        ↓
统一 Issue → 复核 → 报告 → 回写协同
```

## 2. 三条业务技术路径（投标，落地细化）

### 2.1 形式审查与目录一致性

**投标路径（必须）：**

1. **PP-DocLayoutV3** 分割定位标题栏、说明栏、版本栏等；  
2. 裁剪区域送入 **Qwen3.8**，输出结构化 JSON（图号、项目名、阶段、日期等）；  
3. **规则引擎**依据形式审查规则技能校验：必填完整、格式合规、同组一致、图号后缀连续等；  
4. 目录一致性：解析目录 → 与文件夹实体及标题栏结果 **三方交叉比对**（缺图/多图/版本混用）。

**落地细化（不改路径）：**

| 步骤 | 落点 | 说明 |
|------|------|------|
| 文档/图纸预处理 | 工具层 | DOC/DOCX→MD、PDF→PNG；**不注册为审查智能体** |
| 版面分割 | AI 引擎 · 布局分割 | 调用名可统一为 `layout.detect`，**实现=PP-DocLayoutV3** |
| 信息抽取 | AI 引擎 · 多模态 | Qwen3.8 微调任务：标题栏等（投标四向微调之一） |
| 技能校验 | 规则引擎 + 形式审查智能体 | 读 Skill/`checks`，算子 `required_fields`/`eq`/`seq`/`set_diff` 等 |
| 目录三方 | 项目级 Skill | `needs: [toc, file_list, title_block]` |

对应审查点底账：`FORM-*`（见审查点总表）。

### 2.2 工艺自控流程图（P&ID）深度审查

**投标路径（必须）：**

1. **Image-to-Graph** 端到端：像素 → 节点/边（阀门、仪表、设备及管线/信号连接）；  
2. 图结构入 **图数据库**；  
3. **P&ID 规则转换智能体** 将自然语言规则转为图查询/判定逻辑（如 Cypher）；  
4. 审查执行侧完成连通性、流向、错位、缺管、多余连接等拓扑与图面类检查。

**落地细化：**

- I2G 封装为工具/引擎能力，由总控在 `needs` 含 `pid_graph` 时调用；  
- 拓扑类 Skill 使用已登记算子（如 `cypher`）；图面/标注类可与抽取字段 + 规则引擎结合；  
- 关联审查（流程↔平面↔设备表↔说明↔计算书）在同一套执行面上增加跨图工件与 Skill，**不另起总控**。

对应：`PID-*`、`ASSOC-*`。

### 2.3 总平面布置图深度审查

**投标路径（必须）：**

1. **总图规则转换智能体** 将人话解析为：图元类型 + 空间计算指令 + 阈值；  
2. **MCP** 操控 CAD 打开 DWG，筛图层导出与坐标对齐的 PNG；  
3. CV 结合图例语义识别轮廓并回传坐标；  
4. CAD 精确量距/面积，与阈值比较输出结论。

**落地细化：**

- 「CV 懂、CAD 准」闭环保持不变；  
- 空间类 Skill 使用 `min_distance` 等算子；图面/一览表类走抽取 + 规则引擎；  
- 竖向/管综/道路/消防等清单增量按合同阶段纳入，不挤占投标一阶段「典型总平面」主路径表述。

对应：`SITE-*`。

## 3. 总体分层架构（投标六层 + 配套图）

对齐投标「分层解耦、智能协同、持续演进」，配套图：`架构图-系统分层架构.drawio`。

| 层 | 职责（投标） | 落地组件 |
|----|--------------|----------|
| 展现层 | 门户、预览、规则、复核、统计 | Vue 3 + TS + Vite + Element Plus；Canvas/Konva 预览 |
| 服务层 | API、任务、权限、集成 | RuoYi-Vue（Spring Boot 等）；XXL-Job / RabbitMQ；协同网关 |
| 智能体层 | LangGraph 编排六类智能体 | 见第 4 章；唯一入口 `invoke(task)` |
| AI 引擎层 | 布局分割、VLM、I2G、规则转换模型等 | PP-DocLayoutV3、Qwen3.8-27B、Image-to-Graph、向量检索等 |
| 数据层 | 多模存储 | MySQL（验收前迁国产）、图库、MinIO、Redis、规则库、工件库、向量库 |
| 资源层 | 算力与内网安全 | GPU/CPU、对象存储、信创与保密合规 |

微件划分（投标）：解析、规则引擎、形式、PID、总图、报告等可独立部署；**审查点不在各微件内复制一套编排**。

## 4. 智能体层落地设计（六类智能体 × 固定工作流）

> 投标写「六类专业化智能体 + LangGraph」。本章说明**如何实现该叙事且可开发维护**，不减少任一投标智能体职责。

### 4.1 六类智能体（投标）与运行时映射

| 投标智能体 | 面 | 运行时落点 |
|------------|----|------------|
| 形式规则转换智能体 | 编译面 | 规则转换服务 → 产出/改写形式类 Skill → 人确认+回归 → 工作流注册中心 |
| P&ID 规则转换智能体 | 编译面 | 同上，产出拓扑/Cypher 类 Skill |
| 总图规则转换智能体 | 编译面 | 同上，产出空间量距类 Skill |
| 形式审查智能体 | 执行面 | 执行 `pack=form` 的已注册 Skill（规则引擎为主） |
| P&ID 审查智能体 | 执行面 | 执行 `pack=pid` / 关联类 Skill（含图查询） |
| 总图审查智能体 | 执行面 | 执行 `pack=site` 的 Skill（含 CV+CAD 结果判定） |

**总控（编排入口）：** LangGraph 接收服务层任务，按图纸/任务类型调度检测、提取，再扇出到上述审查执行能力，汇聚 Issue。总控是「图的入口」，**不是**让大模型现场自由选工具的 ReAct 环。

### 4.2 两面分离（补充，不违背投标）

| 面 | 何时运行 | 做什么 |
|----|----------|--------|
| **编译面** | 甲方新写/改规则、规则自建 | 3 个规则转换智能体：人话 → 技能描述 → 确认 → 回归 → 写入注册中心 |
| **执行面** | 每一套图审查 | 固定编排：预处理 → 检测 → 抽取 → **按已注册技能校验** → 校验闸门 → 报告 |

已确认审查点（清单/投标已明确）：开发期可直接编写 Skill 入库，**不必每条都先跑转换智能体**；转换智能体仍保留，满足「规则可自建」。

### 4.3 执行面固定工作流（落地）

```
收图/文件夹
  → 工具预处理（MD/PNG/DXF…）          ← 非智能体
  → 图纸检测（PP-DocLayoutV3）         ← AI 引擎，总控编排
  → 信息抽取（Qwen3.8 / I2G / CAD…）   ← 按 Skill.needs 并集，同工件只抽一次
  → 审查执行（形式/P&ID/总图 Skill）   ← 对应三类审查智能体职责
  → 结果校验（schema/置信度/缺件闸门）
  → Issue 汇聚 → 人工复核 → 报告回写
```

**工作流（编排）只写「调用谁」；Skills 写「比什么」。**  
客户改规则 → 改 Skills（或经转换智能体改写）→ 审查执行读到的检查项变化 → **编排边不变**。

配套图：`架构图-审查点开发做法.drawio`、`架构图-智能体框架.drawio`。

### 4.4 三个注册中心（投标可增长点落地）

| 注册中心 | 内容 |
|----------|------|
| 智能体注册中心 | 六类智能体及后续扩展（如新专业审查）只注册、配置开关 |
| 工具注册中心 | 预处理、检测、抽取、I2G、CAD、向量检索等 |
| 工作流注册中心（审查点入口） | 每个审查点一条 Skill/工作流包；开发人员唯一挂载点 |

### 4.5 任务信封（服务层 → 总控）

```text
project_id / task_id / files[] / skill_ids[]（或 workflow_ids[]） / callback
```

- 前端 → 仅后端 API；  
- 后端 → 仅 `invoke(task)`；  
- 返回统一 Issue 列表落库并推送。

## 5. 工具层与图纸解析（补充边界）

投标功能架构含「图纸解析与预处理」。落地约定：

| 工具 | 作用 | 是否智能体 |
|------|------|------------|
| PDF→PNG（如 PyMuPDF） | 图纸页渲染 | 否 |
| DOC/DOCX→MD | 目录/说明书等转文本结构 | 否 |
| CAD/DXF 解析、图层导出 | 总图/部分关联前置 | 否（CAD 协同仍按投标 MCP 路径） |
| 向量检索 | 规范 RAG、图例相似 | 否（引擎能力） |

**原则：** 解析与格式转换进工具注册中心；智能体负责编排、规则转换与审查执行，避免「每个审查点自己调一遍解析」。

## 6. AI 模型与训练（严格按投标）

### 6.1 PP-DocLayoutV3（布局分割）

- 基座：飞桨 PP-DocLayoutV3；实例分割 + 阅读顺序；Apache-2.0。  
- 检测目标（投标）：主图区、图例区、标题栏区、辅助说明区。  
- 训练：甲方工程图微调；标注与增广策略按投标。  
- **本文不改用其它检测器作为对外主选型。**

### 6.2 Qwen3.8-27B（多模态）

- 私有化部署；LoRA 等按投标。  
- 四向微调：标题栏抽取、图例语义、总图构件识别、**规则转换**。  
- 输出结构化 JSON，供规则引擎使用。

### 6.3 Image-to-Graph

- Swin 视觉编码 + Transformer 图解码；节点/边/属性；入图库。  
- 两阶段训练与损失组合按投标；封装为推理服务。

### 6.4 向量库

- 规范条文 RAG + 图例相似；**不用于**目录字段集合比对（比对走规则引擎）。

## 8. 数据与审查结果

### 8.1 规则库

存储机器可执行技能（Skill）：编号、名称、类型、适用图种、自然语言原文、结构化技能 JSON/YAML、规范条款、版本、生效状态等（对齐投标规则库字段设计）。

### 8.2 工件库（落地补充）

检测/抽取产物按名复用，例如：`layout`、`toc`、`title_block`、`file_list`、`legend`、`pid_graph`、`site_features`。  
总控按本次 Skill 的 **`needs` 并集** 调度，禁止每点重复检测抽取。

### 8.3 Issue 统一 Schema（落地补充）

```text
issue_id, drawing_no, skill_id, type, severity, desc, basis,
suggestion, x, y, confidence, review_status
```

扩展字段须平台评审；报告输出 Web 列表 + 图面标记、PDF 批注、Excel 清单；复核状态机与审计按投标/启动会要求。

### 8.4 规则引擎算子（落地）

默认代码算子：`eq` / `regex` / `seq` / `set_diff` / `cypher` / `min_distance` 等；  
`llm_judge` 仅用于错别字、语义、检测失败兜底、美观杂乱等投标允许的语义类点。

## 9. 审查点开发约定（配套图落地）

一人一个审查点 = 向**工作流注册中心**提交包，**不是**新建智能体或新总控。

包最小集：

1. Skill/工作流描述（`id/name/pack/needs/checks` 或投标等价字段）；  
2. 正例、反例图纸各 ≥1；  
3. 回归断言（期望 Issue 类型与数量）。

详见：`AI智能体框架-开发约定.md`、`审查框架/开发指南.md`、`架构图-审查点开发做法.drawio`。

## 10. 功能架构与阶段（对齐投标实施）

| 模块 | 一阶段（至 2026-11-15）侧重 | 二阶段侧重 |
|------|------------------------------|------------|
